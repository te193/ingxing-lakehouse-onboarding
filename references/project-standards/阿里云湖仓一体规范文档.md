## 一、架构总览

### 1.1 当前目标架构

```text
┌─────────────────────────────────────────────────────────────┐
│                      领星 OpenAPI                           │
└──────────────────────────┬──────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────────┐
│                 DataWorks采集与调度                         │
│  PyODPS 3领星接口节点 / ODPS SQL节点 / 数据同步节点          │
└──────────────────────────┬──────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────────┐
│                     OSS原始数据层                           │
│  JSON / Parquet，按数据集和dt=YYYY-MM-DD目录保存            │
└──────────────────────────┬──────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────────┐
│                 MaxCompute EXT技术映射层                    │
│  注册OSS目录并解析JSON或Parquet，只保存元数据，不存业务数据   │
└──────────────────────────┬──────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────────┐
│              MaxCompute DWD明细标准化存储层                 │
│  MaxCompute内部表只存DWD，不建设DWS和ADS                    │
└──────────────────────────┬──────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────────┐
│                       MySQL DWS层                           │
│  宽表 + 数据库数据应用层，承接聚合、关联和高频业务查询       │
└─────────────────────────────────────────────────────────────┘

前端/应用写入 → MySQL ADS层（前端数据写入层）
```

### 1.2 完整链路和架构边界

当前完整路径确定为：

```text
领星 OpenAPI
→ DataWorks PyODPS 3
→ OSS原始数据
→ MaxCompute EXT技术映射
→ MaxCompute DWD明细数据
→ MySQL DWS宽表及数据库数据应用层

前端/应用写入
→ MySQL ADS前端数据写入层
```

各组件边界如下：

- **OSS**：保存领星原始数据，不承担DWD、DWS或ADS业务加工；
- **MaxCompute EXT**：只映射OSS文件和分区，不复制、存储业务数据；
- **MaxCompute DWD**：负责明细标准化，是MaxCompute唯一内部业务数据层；
- **MySQL DWS**：负责宽表建设和数据库数据应用，服务接口、看板、报表及高频查询；
- **MySQL ADS**：负责承接前端或应用产生并写入的数据，不作为MaxCompute离线数仓层；
- 禁止在MaxCompute中建设DWS、ADS内部表；
- MySQL不作为当前链路的上游原始数据源，不承担原始数据归档和大规模离线明细计算。

当前阶段不强制引入：

- EMR；
- DLF；
- Hologres；
- 其他未产生实际业务价值的复杂组件。

是否新增组件，必须根据数据规模、并发、实时性和成本单独评估，不能为了符合通用参考架构而增加复杂度。

## 二、数据接入模式

### 2.1 领星OpenAPI接入

```text
领星OpenAPI
  → DataWorks PyODPS 3节点
  → OSS（少量数据用JSON；其他数据用Parquet+Snappy列式存储）
  → MaxCompute EXT外部表（按实际JSON或Parquet格式做技术映射）
  → ODPS SQL展开和清洗
  → MaxCompute DWD
  → MySQL DWS（宽表 + 数据库数据应用层）

前端/应用写入
  → MySQL ADS（前端数据写入层）
```

当前已落地的领星接口节点：

| 接口节点 | API路径 | OSS存储格式 | 说明 |
|---|---|---|---|
| `lx_basic_seller` | `/erp/sc/data/seller/lists` | JSON单信封 | 店铺列表，不支持分页，一次返回全部 |
| `lx_sales_mws_listing` | `/erp/sc/data/mws/listing` | JSON单信封 | Listing全量，按SID批次拉取后合并写入 |
| `lx_sales_mws_listing_parquet` | `/erp/sc/data/mws/listing` | Parquet+Snappy | Listing的Parquet版本，多SID批次多分片 |
| `lx_basic_account_list` | `/erp/sc/data/account/lists` | Parquet+Snappy | 账号列表，不支持分页 |

适用场景：

- 只能通过HTTP API获取；
- 需要签名、Token、分页和重试；
- 返回JSON或嵌套JSON；
- 需要按接口定制请求参数；
- OSS存储格式按数据量选择：仅少量数据使用JSON单信封，其他数据统一使用Parquet+Snappy列式存储。

#### 2.1.1 分页期间 `total` 变化处理规范

领星分页接口通常使用 `offset + length` 拉取数据。若分页期间源系统新增、删除或更新记录，后续页面返回的 `total` 可能与第一页不一致，同时记录位置也可能发生移动。此时不得继续沿用原 `offset` 拉取并直接合并，否则可能产生漏数、重复或前后时间点不一致的数据。

处理方案按以下三个优先级选择。开发新接口前，必须先确认接口是否提供相应能力；只有上一级不可用时，才使用下一级方案。

**第一优先级：使用源接口快照或游标分页**

若接口提供快照ID、游标、`next_token`、版本号等能力，必须优先使用，并确保同一次同步的所有分页请求使用同一快照或连续游标。

```text
首次请求获取 snapshot_id 或 next_cursor
→ 后续分页持续携带同一快照或上一页游标
→ 当前同步读取固定版本的数据集合
```

该方案能够从源头避免 `offset` 因数据增删而发生位置漂移，是全量大数据接口的首选方案。使用游标时仍需记录请求次数、游标值、每页记录数和最终累计记录数，防止游标重复或中断。

**第二优先级：固定时间水位并使用稳定复合排序**

若接口不支持快照或游标，但支持按创建时间、更新时间等字段过滤，则在任务开始时固定本次同步窗口：

```text
window_start = 上次成功水位
window_end   = 本次任务开始时间
```

本次仅拉取：

```text
update_time > window_start
AND update_time <= window_end
```

运行期间晚于 `window_end` 的变化留到下一次同步处理。分页排序必须稳定，推荐使用 `update_time + 唯一业务ID` 组成复合游标；只按时间字段排序可能因多条记录时间相同而漏数或重复。

```text
update_time > last_update_time
OR (update_time = last_update_time AND id > last_id)
```

水位只能在本次全部数据成功写入、校验并正式发布后推进。失败任务不得更新水位。

**第三优先级：按业务维度拆批，缩小失败重拉范围**

若接口只支持 `offset + length`，无法使用快照、游标或固定时间窗口，则按SID、店铺、站点或其他稳定业务维度拆成小批次。每个批次独立记录首次 `total`、分页进度和最终记录数。

```text
全部SID
├─ 批次1：成功，保留结果
├─ 批次2：成功，保留结果
└─ 批次3：total变化，仅重拉本批次
```

`total` 发生变化时，应执行以下规则：

1. 立即终止当前批次分页，不得从发生变化的 `offset` 继续；
2. 丢弃当前批次本轮未完成结果，从 `offset=0` 重新拉取；
3. 已成功并完成校验的其他批次不得重复拉取；
4. 当前批次连续失败时，可按SID清单二分拆批，逐步缩小到单SID；
5. 单SID仍持续变化时，采用限次重试和退避等待，超过阈值后进入补偿队列或终止本次发布；
6. 不得仅根据多SID请求返回的汇总 `total` 直接判定具体异常SID。接口未提供每SID权威总量时，只能先定位失败批次，再通过拆批重试隔离不稳定范围。

为避免大数据量任务失败后全部重拉，第三优先级方案应配合临时分片和检查点：

```text
_staging/run_id/
├─ batch-00000/part-00000.parquet
├─ batch-00001/part-00000.parquet
├─ checkpoint.json
└─ _manifest.json
```

检查点至少记录：

| 字段 | 说明 |
|---|---|
| `run_id` | 本次同步唯一标识 |
| `batch_id` | 当前业务批次标识 |
| `sid_list` | 当前批次SID清单 |
| `offset` | 当前分页位置，仅用于审计和故障定位 |
| `first_total` | 当前批次第一页返回的总量 |
| `current_total` | 当前页返回的总量 |
| `actual_count` | 当前批次已获取记录数 |
| `status` | `RUNNING`、`COMPLETED`、`TOTAL_CHANGED`或`FAILED` |
| `retry_count` | 当前批次重试次数 |

检查点中的 `offset` 不得作为 `total` 变化后的直接续拉依据，因为源数据位置可能已经移动。它只用于定位故障；异常批次必须从第一页重拉。跨任务复用成功批次时，还必须校验接口请求条件、SID清单、业务日期和代码版本一致，防止复用过期结果。

**通用完整性与发布要求**

无论采用哪个优先级，都必须遵守以下要求：

1. 分页期间发现 `total` 变化时，本轮不完整结果不得写入正式OSS目录；
2. 分页结果优先写入带 `run_id` 的临时目录，全部批次成功后再生成 `_manifest.json` 或复制到正式 `dt` 目录；
3. 正式目录只允许下游读取已成功发布的完整版本，不得读取 `_staging`；
4. 最终按稳定业务主键检查重复，并核对批次记录数、文件数和文件大小；去重只能消除重复，不能补回遗漏，因此不能替代完整性校验；
5. 必须设置最大重试次数、退避间隔、最大页数或最大 `offset`，避免源接口异常导致无限循环；
6. 若业务要求强一致，任一批次失败则整个业务日期不得发布；若允许最终一致性，可发布稳定批次，但必须在清单中标记缺失范围并由补偿任务完成后再更新完整状态；
7. 是否采用强一致发布或最终一致发布，必须由业务方在接口开发前确认，不得由开发人员自行推定。

当前项目实现状态：

- 公共引擎检测到 `total` 变化后会立即抛错；
- Listing JSON版本任一SID批次异常时终止整项任务，不上传残缺 `data.json`；
- Listing Parquet版本会丢弃当前200个SID批次的本轮结果，从第一页重拉，最多尝试3次；全部批次成功前只写临时目录，不发布半成品；
- 失败批次二分、单SID隔离、持久化检查点和跨任务复用成功批次属于推荐增强项，当前尚未正式落地。

### 2.2 当前数据接入边界

当前规范只覆盖领星OpenAPI接入：

```text
领星OpenAPI → OSS → MaxCompute EXT → MaxCompute DWD
```

MySQL位于DWD之后，用于存储DWS和ADS，不再作为当前链路的上游数据源。若未来需要接入文件或其他第三方系统，必须单独评估并更新本规范，不得直接套用已废弃的“MySQL源表到OSS”流程。

### 2.3 接入方案选择原则

| 场景 | 首选方式 |
|---|---|
| 领星HTTP/OpenAPI | PyODPS 3采集到OSS |
| OSS已有规范文件 | 建设MaxCompute EXT外部表进行技术映射 |
| 明细展开、标准化和清洗 | ODPS SQL写入MaxCompute DWD |
| DWD后续宽表和数据应用 | 写入MySQL DWS |
| 前端或应用产生的数据 | 写入MySQL ADS |

不得默认所有领星接口采用同一种策略。每个数据集开发前必须确认：

1. 数据用途；
2. 领星接口能力；
3. 全量还是增量；
4. 是否需要历史；
5. 日期参考字段；
6. 更新频率；
7. 对应的MaxCompute DWD目标表；
8. 是否需要建设MySQL DWS宽表或数据库数据应用；
9. 是否涉及MySQL ADS前端写入数据；
10. 空数据是否属于正常业务情况。

## 三、命名规范

### 3.1 业务数据集命名

统一格式：

```text
{来源}_{接口一级目录}_{接口名称}
```

要求：

- 全部使用小写英文和下划线；
- 不在接口名中添加 `sync`、`df`、`di`；
- 名称能够从接口路径或业务域反向识别；
- 同一数据集在Python、OSS、EXT、DWD和DataWorks中保持核心名称一致；
- MySQL DWS和ADS按各自业务用途命名，不要求与DWD机械同名，但必须记录来源表、目标表和加工关系。

示例：

```text
lx_basic_seller
lx_sales_mws_listing
lx_basic_account_list
```

### 3.2 OSS目录设计规则

#### 3.2.1 目录层级结构

统一格式：

```text
oss://{bucket}/{root_prefix}/{dataset}/dt=YYYY-MM-DD/{file}
```

当前实际配置：

```text
Bucket：     gq-lakehouse
Endpoint：   oss-cn-shenzhen-internal.aliyuncs.com（DataWorks内网访问）
根前缀：     guqiao_ods
```

完整层级说明：

| 层级 | 示例 | 说明 |
|---|---|---|
| Bucket | `gq-lakehouse` | 当前唯一Bucket，不按环境拆分 |
| 根前缀 | `guqiao_ods` | 所有原始数据的统一根前缀 |
| 数据集 | `lx_basic_seller` | 与业务数据集命名一致（见3.1节） |
| 日期分区 | `dt=2026-08-14` | Hive风格分区目录 |
| 文件 | `data.json` / `part-00000.parquet` | 见3.6节文件命名规则 |

实际示例：

```text
oss://gq-lakehouse/guqiao_ods/lx_basic_seller/dt=2026-08-13/data.json
oss://gq-lakehouse/guqiao_ods/lx_sales_mws_listing/dt=2026-08-13/data.json
oss://gq-lakehouse/guqiao_ods/lx_sales_mws_listing_parquet/dt=2026-08-13/part-00000.parquet
oss://gq-lakehouse/guqiao_ods/lx_basic_account_list/dt=2026-08-13/part-00000.parquet
```

#### 3.2.2 dt分区定义

`dt`统一表示**业务日期**，其值直接取DataWorks调度参数`biz_date`，不是节点实际运行日期。

```text
dt = DataWorks调度参数 biz_date 的值
```

当前任务在次日凌晨处理前一天的数据，DataWorks节点参数配置为：

```text
参数名：biz_date
参数值：$[yyyy-mm-dd-1]
```

`$[yyyy-mm-dd-1]`表示实例定时时间对应的前一天业务日期。例如节点实例的定时时间为`2026-08-14`凌晨，则`biz_date`替换为`2026-08-13`，OSS目录为`dt=2026-08-13`。补数据、重跑或手动测试时必须先确认实例定时时间及参数替换结果，不得直接使用实际点击运行的日期推算业务日期。

整条领星到DWD链路必须使用同一个`biz_date`值：

```text
DataWorks参数 biz_date
= Python节点 args['biz_date']
= OSS目录 dt
= EXT分区 dt
= DWD SQL中 ${biz_date}
```

文件正文是否包含`biz_date`取决于实际Schema：JSON信封和当前由Python生成的Parquet应写入该字段，并与目录`dt`一致；若数据集成生成的Parquet未包含`biz_date`列，则以OSS目录和EXT分区`dt`作为业务日期，不得在EXT中虚构文件不存在的字段。

Python代码不得对传入的`biz_date`再次加一天或减一天。MySQL DWS从DWD同步或加工时，应保留该业务日期或建立明确的批次日期映射；MySQL ADS属于前端数据写入层，其业务时间和写入时间按应用业务定义，不强制套用离线链路的`biz_date`。

#### 3.2.3 目录设计禁止事项

- 使用中文目录名；
- 同一项目混用 `YYYYMMDD` 和 `YYYY-MM-DD`；
- 省略 `dt=`；
- 把临时文件写入正式数据集目录；
- 同一数据集使用多个未说明的根前缀；
- 在数据集目录下创建非日期分区的子目录。

### 3.3 MaxCompute表命名

MaxCompute启用Schema，层级由Schema表达，表名不重复添加层级前缀：

```text
ext.{dataset}_raw
dwd.{dataset}
```

示例：

```text
ext.lx_basic_seller_raw
dwd.lx_basic_seller
ext.lx_sales_mws_listing_raw
dwd.lx_sales_mws_listing
```

### 3.4 DataWorks节点和本地文件命名

每个领星接口在本地使用独立的 `{dataset}/` 文件夹，接口专属的Python、EXT DDL、DWD DDL和DWD ETL全部放入该文件夹。全局规范、迁移台账、公共资源和设计文档继续保留在项目公共目录，不复制到各接口文件夹。

```text
{dataset}/
├─ {dataset}.py
├─ ext_{dataset}_ddl.sql
├─ dwd_{dataset}_ddl.sql
└─ dwd_{dataset}_etl.sql
```

一个接口拆分多张DWD表时，相关DDL和ETL仍统一放在该接口文件夹中。DataWorks节点和文件保留层级前缀，便于搜索和运维识别：

```text
接口目录：lx_basic_seller/
采集节点：lx_basic_seller
Python：lx_basic_seller/lx_basic_seller.py
EXT DDL：lx_basic_seller/ext_lx_basic_seller_ddl.sql
DWD DDL：lx_basic_seller/dwd_lx_basic_seller_ddl.sql
DWD ETL：lx_basic_seller/dwd_lx_basic_seller_etl.sql
DWD节点：dwd_lx_basic_seller
DWD到MySQL DWS：dwd_to_dws_{目标表名}
MySQL ADS：ads_{业务用途}
```

### 3.5 Python资源命名

```text
公共配置：project_config.py
公共引擎：lx_sync_engine.py
接口节点：{dataset}.py
```

资源引用名称必须带 `.py` 后缀：

```python
##@resource_reference{"project_config.py"}
##@resource_reference{"lx_sync_engine.py"}
```

### 3.6 OSS文件命名规则

OSS中每个 `dt=YYYY-MM-DD` 目录下的文件命名按存储格式和落盘方案区分：

#### 3.6.1 JSON单信封文件

```text
data.json
```

固定文件名，不可变。整个JSON信封写为一行紧凑JSON，UTF-8编码。

当前使用此命名的数据集：

```text
lx_basic_seller
lx_sales_mws_listing
```

#### 3.6.2 JSON流式NDJSON分片文件

```text
part-00000.json
part-00001.json
part-00002.json
...
_manifest.json
```

- `part-*.json`：NDJSON格式，每行一条完整业务记录；
- `_manifest.json`：清单文件，记录批次元数据，不作为业务明细读取；
- 分片编号从 `00000` 开始，5位补零。

当前项目中方案B尚无正式落地的领星接口实例。

#### 3.6.3 Parquet文件

```text
part-00000.parquet
part-00001.parquet
...
```

- 分片编号从 `00000` 开始，5位补零；
- 使用Snappy压缩；
- 每个分片对应一个SID批次或一批数据；
- 重跑时先清理`biz_date`对应目录再写入（`delete_prefix` + 重新上传）。

当前使用Parquet的数据集：

```text
lx_basic_account_list          （领星API → Parquet，单分片）
lx_sales_mws_listing_parquet   （领星API → Parquet，多SID批次多分片）
```

#### 3.6.4 临时文件

临时文件统一写入 `_staging/` 子目录：

```text
{dataset}/_staging/{run_id}/part-00000.parquet
```

`run_id` 使用时间戳格式 `YYYYMMDDHHmmss`。全部批次成功后才复制到正式 `dt=` 目录，失败时清理临时目录。正式 `dt=` 目录中不得残留临时文件。

## 四、OSS原始数据层规范

### 4.1 OSS职责

OSS原始层负责：

- 保存未经业务加工的源数据；
- 为问题追溯和补数提供依据；
- 将数据采集与MaxCompute计算解耦；
- 作为JSON和Parquet文件的统一落地点。

OSS只做必要的技术包装，不做业务清洗。

### 4.1.1 存储格式规范

OSS原始数据层统一按数据量选择存储格式：**仅少量数据使用JSON，其他数据使用Parquet+Snappy列式存储**。

| 格式 | 适用范围 | 当前使用的数据集 | 压缩 | 说明 |
|---|---|---|---|---|
| JSON单信封 | 少量数据 | `lx_basic_seller` | 无 | 一行紧凑JSON，包含信封元数据和`data`数组 |
| Parquet+Snappy | 除少量数据外的其他数据 | `lx_basic_account_list`、`lx_sales_mws_listing_parquet` | Snappy | 默认列式存储，按明确Schema写入，可按批次分片 |

格式选择原则：

1. 只有经评估确认属于少量数据的接口才允许使用JSON单信封；
2. 除少量数据外，其他接口统一采用Parquet+Snappy列式存储，不以“中等数据量”作为继续使用JSON的理由；
3. JSON不作为大数据量接口的正式存储方案，NDJSON不作为当前默认或正式落地方案；
4. 因原始响应保真或排障重放需要保留JSON时，只能作为短期辅助副本，正式分析数据仍采用Parquet+Snappy；
5. 每个新接口必须在设计中明确记录数据量评估结果和最终存储格式，AI不得自行猜测。

Parquet写入技术要求：

- 使用PyArrow构建Schema和写入文件；
- 压缩方式：`snappy`；
- 启用字典编码：`use_dictionary=True`；
- 启用统计信息：`write_statistics=True`；
- 支持嵌套类型：`LIST<STRUCT>` 和 `ARRAY<STRING>`；
- 每个SID批次生成一个独立分片文件，文件名 `part-{batch_no:05d}.parquet`；
- 写入前先写 `_staging/` 临时目录，全部成功后复制到正式 `dt=` 目录。

### 4.3 Parquet文件

除已确认的少量数据接口外，其他领星接口统一采用Parquet+Snappy列式存储：

- 使用明确的PyArrow Schema保持字段类型稳定；
- 不在文件层做复杂业务计算；
- 每个业务日期写入独立的`dt=YYYY-MM-DD`目录；
- 重跑前必须明确覆盖、清理或幂等策略。

### 4.4 保留策略

OSS原始数据的保留期按数据价值、合规和成本单独确定。即使DWD只保留最新值，OSS仍可按日保留原始文件用于追溯。

不得把“DWD不保留历史”等同于“OSS也不保留历史”。

### 4.5 OSS访问

同地域DataWorks访问OSS使用内网Endpoint：

```text
oss-cn-shenzhen-internal.aliyuncs.com
```

正式代码中完整URI示例：

```text
oss://oss-cn-shenzhen-internal.aliyuncs.com/gq-lakehouse/guqiao_ods/lx_basic_seller/
```

## 五、MaxCompute EXT外部表规范

### 5.1 EXT职责

EXT是OSS进入MaxCompute的技术映射层：

- 外部表只保存表结构和LOCATION映射；
- 不重复复制OSS原始数据；
- 不承担复杂业务加工；
- 统一按 `dt` 分区定位每日OSS目录；
- DDL原则上只初始化一次。

### 5.2 JSON外部表

API JSON统一使用：

```sql
ROW FORMAT SERDE 'org.apache.hive.hcatalog.data.JsonSerDe'
STORED AS TEXTFILE
```

#### 单JSON信封EXT

信封方案将 `data` 数组按实际返回结构定义：

```sql
data ARRAY<STRUCT<
    sid:BIGINT,
    name:STRING
>>
```

文件白名单可匹配`biz_date`对应目录中的`data.json`。

#### 流式NDJSON分片EXT

NDJSON方案直接将每行定义为一条业务记录，不定义信封元数据和 `data ARRAY<STRUCT>`。文件白名单必须只匹配业务分片，例如：

```sql
'odps.external.data.file.whitelist.regex' = 'part-.*\\.json'
```

不得读取 `_manifest.json`。

两种JSON外表都必须开启外部数据扩展：

```sql
TBLPROPERTIES
(
    'odps.external.data.enable.extension' = 'true',
    'odps.external.data.file.whitelist.regex' = '<按实际方案配置>'
)
```

### 5.3 Parquet外部表

结构化源文件使用：

```sql
STORED AS PARQUET
```

EXT字段名称和数据类型必须与写入OSS的Parquet结构一致。

### 5.4 EXT分区注册

外表固定保留，每日DWD ETL开始前注册`biz_date`对应目录：

```sql
ALTER TABLE ext.{dataset}_raw
ADD IF NOT EXISTS PARTITION (dt = '${biz_date}')
LOCATION 'oss://oss-cn-shenzhen-internal.aliyuncs.com/gq-lakehouse/guqiao_ods/{dataset}/dt=${biz_date}/';
```

禁止每天DROP并重建整个外部表。

## 六、MaxCompute DWD规范

### 6.1 DWD职责

DWD负责：

- 展开嵌套数组；
- 字段白名单映射；
- 数据类型转换；
- 空字符串标准化；
- 状态编码转换；
- 主键和溯源ID生成；
- 关联必要的基础维度；
- 按业务需要保留最新数据或历史快照。

当前标准实现方式为DataWorks **ODPS SQL节点**，不再把PyODPS/Pandas作为通用DWD写入模板。

### 6.2 表类型选择

#### 最新状态表

适用：其他接口参数表、配置表、只查询当前状态的明细表。

```sql
INSERT OVERWRITE TABLE dwd.{table}
SELECT ...;
```

示例：

```text
dwd.lx_basic_seller
dwd.lx_sales_mws_listing
```

#### 每日历史快照表

适用：库存、价格、状态变化分析和需要按日重跑的数据。

```sql
INSERT OVERWRITE TABLE dwd.{table} PARTITION (dt = '${biz_date}')
SELECT ...;
```

示例：

```text
dwd.lx_storage_fba_warehouse_detail
```

表是否分区必须由业务用途决定，禁止因为任务每日运行就默认建历史分区。

### 6.3 DWD DDL规范

每个表至少说明：

- 表名；
- 业务用途；
- 数据来源；
- 数据粒度；
- 同步方式；
- 是否保留历史；
- 主键或唯一键口径。

DDL基础设置：

```sql
SET odps.namespace.schema = true;
SET odps.sql.type.system.odps2 = true;
```

基础类型映射：

| 业务类型 | MaxCompute类型 |
|---|---|
| 整数ID/数量 | `BIGINT` |
| 文本 | `STRING` |
| 金额/比例 | `DECIMAL(p,s)` |
| 时间 | `DATETIME` |
| 日期分区 | `STRING`，格式 `YYYY-MM-DD` |
| 布尔值 | `BOOLEAN` |

字段和中文注释以已确认的源表或业务定义为准，不得擅自改名或改口径。

### 6.4 DWD清洗SQL结构

推荐顺序：

```text
1. 设置MaxCompute运行参数
2. 注册`biz_date`对应的EXT分区
3. 执行空源检查
4. 读取和展开源数据
5. 技术性清洗及业务转换
6. 写入DWD
7. 执行结果核验
```

JSON数组展开：

```sql
LATERAL VIEW POSEXPLODE(raw.data) exploded AS pos, item
```

使用 `POSEXPLODE` 而不只是 `EXPLODE`，可以获得稳定行号 `pos`，用于生成批次内唯一ID和溯源ID。

### 6.5 字段清洗

文本字段：

```sql
NULLIF(TRIM(item.name), '')
```

枚举字段：

```sql
CASE
    WHEN item.status = 0 THEN '停售'
    WHEN item.status = 1 THEN '在售'
    ELSE NULL
END
```

时间字段：

```sql
CAST(sync_time AS DATETIME)
```

复杂数组按业务需要使用：

- `POSEXPLODE`；
- `FROM_JSON`；
- `TRANSFORM`；
- `CONCAT_WS`；
- 条件聚合。

### 6.6 ID与溯源规范

当前DWD根据已确认的领星接口结构和DWD业务定义，可包含：

- `id`：业务主键或MaxCompute侧生成的Snowflake兼容ID；
- `relate_id`：源记录ID或按“业务日期+行号”生成的溯源ID。

API数组无源主键时，可按当前实现生成：

```text
relate_id = yyyyMMdd（8位） + data数组行号（7位）
```

有可靠源主键时，优先将源主键写入 `relate_id`。

ID生成规则必须满足：

- 同一批次唯一；
- 指定日期重跑稳定；
- 不依赖不可控的随机顺序；
- 与最终MySQL主键策略兼容。

### 6.7 空源保护

所有 `INSERT OVERWRITE` 任务必须评估空源风险。

历史分区表可在覆盖`biz_date`对应分区前执行：

```sql
SELECT
    CASE
        WHEN COUNT(*) = 0 THEN CAST('EMPTY_OSS_SOURCE' AS BIGINT)
        ELSE COUNT(*)
    END AS source_record_count
FROM ext.{dataset}_raw
WHERE dt = '${biz_date}';
```

最新全量表同样必须在整表覆盖前阻断异常空源。若接口业务上允许0条数据，需要另行确定保护规则，不可直接套用 `COUNT(*) > 0`。

### 6.8 质量检查

至少检查：

```sql
SELECT
    COUNT(*) AS row_count,
    COUNT(DISTINCT {business_key}) AS distinct_key_count,
    SUM(CASE WHEN {business_key} IS NULL THEN 1 ELSE 0 END) AS null_key_count,
    COUNT(DISTINCT id) AS distinct_id_count,
    COUNT(DISTINCT relate_id) AS distinct_relate_id_count,
    MAX(create_time) AS latest_sync_time
FROM dwd.{table}
WHERE dt = '${biz_date}';
```

普通表不带 `dt` 条件。

质量规则应包括：

- 源数据非空或符合业务预期；
- 主键非空；
- 主键无重复；
- 行数波动在合理范围；
- 同步日期正确；
- 源记录数与目标记录数差异可解释；
- 金额、数量、状态枚举符合业务范围。

#### 6.8.1 DWD完成后的源端一致性校验

DataWorks中的DWD任务完成后，必须以同一领星接口快照或已成功发布的OSS原始批次为边界，与MaxCompute DWD结果进行一致性校验：

```text
领星OpenAPI或OSS原始批次 ↔ MaxCompute DWD表
MaxCompute DWD校验通过后 → 允许下游MySQL DWS加工或同步
```

该校验是DWD任务的质量闭环，不得仅以“DataWorks节点运行成功”或“DWD表有数据”作为同步成功依据。节点成功只表示SQL执行完成，不能证明数据没有遗漏、重复或转换错误。

**校验边界要求**

源端和DWD端必须比较同一个数据范围：

- 全量最新状态表：使用同一一致性快照、固定查询时点或可解释的源端统计口径；
- 增量表：使用相同的 `window_start` 和 `window_end`；
- 每日快照表：使用相同`biz_date`、接口请求窗口及店铺/站点等筛选条件；
- 领星分页接口：使用本次采集的快照、游标、固定水位或已成功发布的OSS原始批次作为源端基准；禁止在DWD完成后直接查询持续变化的领星实时总量，再与早先采集的DWD结果机械比较。

若领星源系统持续变化且无法提供快照，应优先将“本次已成功发布的OSS原始批次”作为直接技术源进行逐层校验，同时对领星源端执行带固定条件的业务对账。无法固定比较边界时，必须在校验结果中标注口径差异，不得直接判定DWD不一致。

**每批次必须执行的基础校验**

| 校验项 | 领星或OSS原始批次 | DWD端 |
|---|---|---|
| 记录数 | 接口`total`、实际拉取数、信封`record_count`或清单记录数 | 同一分区/范围`COUNT(*)` |
| 业务主键数 | 按接口稳定业务键统计 | `COUNT(DISTINCT business_key)` |
| 主键空值与重复 | 检查接口或原始文件业务键 | 检查DWD主键空值与重复 |
| 时间边界 | 请求窗口及返回数据时间范围 | 对应字段最小/最大值 |
| 关键指标 | 可由原始记录汇总的金额、数量和状态分布 | 使用同口径汇总 |

源记录数与DWD记录数不要求在所有场景机械相等。发生以下转换时，必须预先定义可解释的数量关系：

- 一条源记录中的数组展开为多条DWD记录；
- 源端重复数据在DWD按业务主键去重；
- 无效记录、逻辑删除记录或不符合业务条件的数据被过滤；
- 多个源记录聚合为一条DWD记录；
- 关联维表失败的数据进入隔离区或被明确阻断。

例如数组展开场景应比较：

```text
DWD记录数
= 源端各记录中有效数组元素数量之和
```

而不是直接要求DWD行数等于源端JSON外层记录数。

**分级深度校验**

1. 所有表每批次执行基础校验：任务状态、记录数、业务主键数、主键空值/重复、时间边界、分区日期和Schema；
2. 订单、库存、利润、结算等核心表每批次增加金额、数量、状态分布及店铺/站点维度汇总校验；
3. 高风险表、周期审计和异常排查增加分桶哈希或关键字段哈希；
4. 全字段逐行比对不要求每次对所有表执行，应根据数据量、源端压力和业务风险安排周期性校验。

哈希校验必须先统一字段顺序、`NULL`、空字符串、小数精度、时间格式、时区和字符编码。大表应按稳定业务主键分桶，对比每桶记录数与摘要；发现异常后只下钻异常桶到主键级。哈希校验必须与记录数、主键数和关键业务汇总联合使用，不得作为唯一判断依据。

**校验失败处理**

发现以下任一情况时，DWD结果不得进入后续正式同步或应用消费：

- 记录数或预定义数量关系不成立；
- 业务主键缺失或异常重复；
- 核心金额、数量等汇总超出容差；
- 分桶哈希或关键字段哈希不一致且无法解释；
- 比较范围、时间水位或业务口径不一致。

处理流程：

```text
DWD任务完成
→ 执行源端与DWD一致性校验
→ 校验通过：允许下游节点继续
→ 校验失败：阻断下游、记录差异范围、告警并重跑或补数
```

校验失败时不得推进增量水位，不得覆盖上一有效版本。修复后必须对相同范围重新校验。若业务允许带缺失数据先发布，必须由业务方明确确认最终一致性方案，并记录缺失范围、补偿任务和完成状态。

**执行与权限要求**

- 领星源端校验只允许执行只读接口调用；
- MySQL DWS同步结果需要核验时，只能使用经批准的只读数据源账号，不使用个人高权限账号；
- 领星校验使用与采集任务一致的数据权限、店铺范围和请求口径；
- 校验查询应限定字段、日期、主键范围和店铺，避免无条件扫描生产大表或高频调用接口；
- 领星接口存在限流时，优先复用采集阶段记录的 `total`、`record_count`、批次清单和原始OSS数据，周期性再回查源端，避免每个DWD任务完成后重新全量拉取接口；
- 校验结果统一记录源端数量、DWD数量、差异值、差异率、校验口径、运行时间和最终状态，便于审计和补偿。

### 6.9 MaxCompute表结构设计规范

#### 6.9.1 Schema使用

MaxCompute启用Schema，层级由Schema表达，表名不重复添加层级前缀：

```text
ext.{dataset}_raw     -- 外部表
dwd.{dataset}         -- DWD内部表
```

当前项目Schema配置（来自 `project_config.py`）：

```text
MC_PROJECT     = df_cs_306350
MC_SCHEMA_EXT  = ext
MC_SCHEMA_DWD  = dwd
```

#### 6.9.2 DDL基础设置

所有DDL文件开头必须包含：

```sql
SET odps.namespace.schema = true;
SET odps.sql.type.system.odps2 = true;
```

EXT外部表和涉及Hive兼容的表还需加：

```sql
SET odps.sql.hive.compatible = true;
```

#### 6.9.3 字段类型映射

| 业务类型 | MaxCompute类型 | 说明 |
|---|---|---|
| 整数ID/数量 | `BIGINT` | 包括 `id`、`sid`、`mid`、各种数量字段 |
| 文本 | `STRING` | 领星接口中的文本字段统一映射为STRING |
| 金额/比例 | `DECIMAL(12,2)` | DWD层精度；EXT层源数据可能为 `DECIMAL(38,18)` |
| 时间 | `DATETIME` | `create_time` 等时间字段 |
| 日期分区 | `STRING` | 格式 `YYYY-MM-DD` |
| 布尔值 | `BOOLEAN` | EXT层 `delete_flag` 等 |
| 嵌套数组 | `ARRAY<STRUCT<...>>` | EXT层JSON信封中的data字段 |
| 嵌套数组 | `ARRAY<STRING>` | 如 `seller_category_new` |

EXT层和DWD层的类型可能不同。EXT层保持与OSS原始文件一致，DWD层按业务口径转换。例如：

- EXT层 `total_price` 为 `DECIMAL(38,18)`（源系统精度），DWD层转为 `DECIMAL(12,2)`；
- EXT层 `share_type` 为 `BIGINT`，DWD层转为 `STRING`（'非共享'/'北美共享'/'欧洲共享'）；
- EXT层 `status` 为 `BIGINT`，DWD层转为 `STRING`（'停售'/'在售'）。

#### 6.9.4 字段和注释规范

- 字段名和中文注释以已确认的领星接口定义及DWD业务口径为准，不得擅自改名或改口径；
- DWD字段顺序必须在建表设计中固化，后续变更需同步更新EXT映射、清洗SQL和下游MySQL DWS；
- 新增技术字段（如`id`、`relate_id`、`create_time`）需在DDL注释中说明来源和用途；
- 每个DDL文件头部必须注释：表名、用途、来源、粒度、同步策略、结构基准。

#### 6.9.5 分区设计

| 表类型 | 是否分区 | 分区字段 | 示例 |
|---|---|---|---|
| 最新状态表 | 不分区 | 无 | `dwd.lx_basic_seller`、`dwd.lx_sales_mws_listing` |
| 每日历史快照表 | 分区 | `dt STRING` | `dwd.{需要保留历史的领星数据集}` |
| EXT外部表 | 分区 | `dt STRING` | 所有EXT表 |

分区字段固定为`dt`，类型`STRING`，格式`YYYY-MM-DD`，值为`biz_date`对应的业务日期。

表是否分区由业务用途决定，禁止因为任务每日运行就默认建历史分区。

#### 6.9.6 DWD表结构基准

DWD表结构以已确认的领星接口返回结构、OSS原始文件Schema和DWD业务口径为依据：

```text
领星接口字段
→ OSS JSON/Parquet Schema
→ MaxCompute EXT映射
→ MaxCompute dwd.{table}
```

要求：

- 领星接口字段必须在EXT中完整、准确映射；
- DWD字段名称、顺序、类型和中文注释必须经过设计确认；
- 类型按6.9.3节映射规则转换；
- 不得为了兼容历史临时表改用`_new`等名称；
- 不得擅自增删业务字段或改变业务口径；
- DWD结构变化必须评估并同步更新下游MySQL DWS。

技术字段（非领星接口原始字段）的增减必须在DDL注释中说明原因。当前实际存在的技术字段：

| 技术字段 | 类型 | 用途 | 存在的表 |
|---|---|---|---|
| `id` | `BIGINT` | Snowflake兼容主键 | 所有DWD表 |
| `relate_id` | `BIGINT` | 溯源ID（源记录ID或日期+行号） | 所有DWD表 |
| `create_time` | `DATETIME` | 同步时间（来自OSS信封sync_time） | 所有DWD表 |

## 七、MySQL DWS与ADS规范

### 7.1 MySQL定位

MySQL负责存储MaxCompute DWD之后的DWS，以及前端或应用写入的ADS。MySQL不承担领星原始数据归档，不作为当前链路的上游源系统，也不承担大规模离线明细计算。

逻辑边界：

```text
MaxCompute DWD → MySQL DWS
前端/应用写入 → MySQL ADS
```

### 7.2 DWS定义：宽表 + 数据库数据应用层

MySQL DWS同时承担两类职责：

1. **宽表层**：基于MaxCompute DWD明细进行跨表关联、维度补充、汇总和主题宽表建设；
2. **数据库数据应用层**：为应用接口、看板、报表、高频查询和既有业务系统提供稳定、可直接查询的数据。

DWS要求：

- 输入数据必须来自已完成质量校验的MaxCompute DWD；
- 一张DWS表必须明确业务主题、统计粒度、主键或业务唯一键、更新策略和来源DWD表；
- 明确采用全量覆盖、增量写入或按业务日期更新；
- MaxCompute分区字段同步到MySQL时通常作为普通业务日期字段；
- DWS加工或同步任务必须依赖对应DWD节点成功；
- 同步后必须核验DWD输入与DWS输出的预期数量关系和关键业务汇总；
- 宽表关联、聚合或过滤导致行数变化时，必须提前定义可解释的数据关系，不要求机械逐行相等。

### 7.3 ADS定义：前端数据写入层

MySQL ADS用于承接前端或应用产生并写入的数据，例如用户配置、操作结果、人工维护内容或应用流程数据。

ADS要求：

- ADS的写入主体是前端或后端应用服务，不是MaxCompute离线加工任务；
- 前端不得直接持有数据库账号连接MySQL，应通过受控后端接口完成校验和写入；
- 每张ADS表必须明确写入接口、业务主键、幂等规则、状态流转、审计字段和数据权限；
- ADS数据应区分业务发生时间与数据库写入时间；
- ADS不强制使用离线链路的`biz_date`，日期口径按前端业务定义；
- 未经单独设计确认，不得默认将DWS结果批量写入ADS，也不得用ADS反向覆盖DWD；
- ADS需要参与DWS查询或计算时，必须建立明确的字段映射、关联键和数据血缘。

### 7.4 DWS与ADS边界

| 层级 | 存储位置 | 主要来源 | 主要职责 | 主要写入方式 |
|---|---|---|---|---|
| DWD | MaxCompute | OSS原始数据 | 明细标准化、基础清洗、历史明细 | ODPS SQL |
| DWS | MySQL | MaxCompute DWD | 宽表、聚合、数据库数据应用 | DataWorks同步或经确认的加工任务 |
| ADS | MySQL | 前端/应用 | 前端数据写入和应用流程数据 | 受控后端接口 |

禁止事项：

- 禁止在MaxCompute中创建DWS或ADS内部业务表；
- 禁止将ADS定义为传统的MaxCompute数据集市层；
- 禁止前端绕过应用服务直接写MySQL；
- 禁止在未定义血缘和口径时混用DWS查询数据与ADS写入数据。

### 7.5 类型映射

| MaxCompute DWD | MySQL DWS建议类型 |
|---|---|
| `BIGINT` | `BIGINT` |
| `STRING` | `VARCHAR(n)` / `TEXT` |
| `DECIMAL(p,s)` | `DECIMAL(p,s)` |
| `DATETIME` | `DATETIME` |
| `BOOLEAN` | `TINYINT(1)` |
| 分区`dt STRING` | `DATE`或`VARCHAR(10)`，按消费方式确定 |

### 7.6 MySQL表规范

- DWS和ADS表必须使用所属数据库中已确认的命名规范；
- 业务表主键方案必须明确；
- 新增应用表的`id`使用`UUID_SHORT()`，禁止自增ID；
- 字段中文注释以已确认口径为准；
- 字段顺序遵守项目数据库规范；
- DWS数据库连接统一配置为DataWorks数据源；
- ADS数据库连接和写权限由受控后端应用管理；
- 用户名和密码禁止写入SQL、Python、前端代码和普通配置文件。

DWS和ADS正式任务落地后，必须补充实际同步或写入配置、血缘关系及核验规则。

### 8.3 调度参数

当前DataWorks节点统一使用参数名：

```text
biz_date
```

参数值已确认为：

```text
$[yyyy-mm-dd-1]
```

`$[yyyy-mm-dd-1]`表示实例定时时间对应的前一天业务日期。例如节点实例的定时时间为`2026-08-14`凌晨，则`biz_date`替换为`2026-08-13`。该表达式基于实例定时时间计算；补数据、重跑和手动测试均应检查参数替换结果。

该日期作为领星到MaxCompute DWD链路的统一业务日期标识：

```text
DataWorks参数 biz_date
= Python节点 args['biz_date']
= OSS目录 dt
= EXT分区 dt
= DWD SQL中 ${biz_date}
```

JSON信封和当前Python生成的Parquet应在文件Schema中保存`biz_date`并与`dt`一致；文件Schema不含该列的数据集成Parquet只通过目录和分区`dt`传递业务日期。

Python节点和SQL节点直接使用参数替换结果，不得再次执行日期加减。MySQL DWS需要保留或明确映射该业务日期；MySQL ADS按前端业务的发生时间和写入时间管理，不强制使用该参数。

正式调度参数名统一使用`biz_date`。为兼容存量节点和DataWorks不同运行入口，代码按`args['biz_date']`、存量别名`args['bizdate']`、环境变量`SKYNET_BIZDATE`的顺序读取。三者均不存在时，普通开发台直接运行可使用当天日期并打印明确提示；调度、补数据和冒烟测试应能够取得业务日期，不得依赖当天兜底。`SKYNET_GMTDATE`表示当前日期，不得作为补数据业务日期来源。代码必须严格校验合法日期：

```python
import os
from datetime import datetime

node_args = globals().get("args") or {}
value = str(
    node_args.get("biz_date")
    or node_args.get("bizdate")
    or os.getenv("SKYNET_BIZDATE")
    or ""
).strip()
if not value:
    value = datetime.now().strftime("%Y-%m-%d")
    print(f"未收到biz_date，普通运行自动使用当天日期: {value}")

if len(value) == 8 and value.isdigit():
    value = f"{value[:4]}-{value[4:6]}-{value[6:]}"

try:
    biz_date = datetime.strptime(value, "%Y-%m-%d").strftime("%Y-%m-%d")
except ValueError as exc:
    raise ValueError(f"biz_date格式错误或日期非法: {value}") from exc
```

SQL引用方式：

```sql
'${biz_date}'
```

必须确认DataWorks替换后的结果为合法的`YYYY-MM-DD`日期，SQL中不得再次使用日期函数加减。

### 8.4 调度时间与依赖

下游实例执行必须同时满足：

1. 已到达下游定时时间；
2. 同周期上游实例运行成功；
3. 调度和计算资源可用。

近似公式：

```text
下游开始时间 ≈ max(下游定时时间, 上游成功时间) + 资源排队时间
```

调度时间不能替代上下游依赖。即使上下游时间间隔较大，也必须配置依赖。

事件调度器或任务具体执行时间必须由用户确认，禁止开发人员擅自决定。

### 8.5 节点输出和依赖

- 上游节点必须配置稳定、可读、唯一的本节点输出；
- 下游选择真实上游业务节点输出；
- 不把DDL文件、下游SQL文件或无关数字输出当作上游；
- 重复输出中保留已有下游引用的输出；
- 删除无下游引用的重复输出时插入 `-- @exclude_output`，避免自动解析后再次生成；
- 发布后在运维中心检查DAG。

示例：

```text
lx_basic_seller
    ↓
dwd_lx_basic_seller
    ↓
dwd_lx_sales_mws_listing
    ↓
dwd_to_dws_{目标表名}

前端/应用
    ↓
受控后端接口
    ↓
MySQL ADS
```

实际DAG必须依据字段和任务依赖建立，不按目录顺序推断。

### 8.6 DDL与ETL文件

本地保留独立的DDL和ETL文件，便于：

- 初始化；
- 结构变更审计；
- 代码评审；
- 灾难恢复。

在小型项目的DataWorks节点中，简单表可将幂等 `CREATE TABLE IF NOT EXISTS` 与每日清洗SQL合并；复杂表、频繁变更表和严格发布审计场景仍应拆分。

### 9.1 使用目的和约束

本章用于同事或AI读取本规范后生成新接口代码时参考。标准样例选用当前已落地的`lx_basic_seller`链路。该接口属于**少量数据场景**，因此示例使用JSON单信封：

```text
→ MaxCompute EXT
→ MaxCompute DWD
```

> `lx_basic_seller`中的JSON代码仅作为少量数据接口的参考。AI生成任何其他接口前必须先判断数据量；未明确确认为少量数据时，默认生成Parquet+Snappy列式存储方案，不得直接照搬JSON单信封。

AI生成新代码时必须遵守：

1. 先复用本章的文件拆分、执行顺序、参数传递、OSS路径和SQL结构，再替换接口路径、字段及业务规则，禁止脱离框架随机生成；
2. 新接口仍需逐项确认接口方法、请求参数、分页能力、同步方式、历史策略、DWD粒度和唯一键，不得因参考接口不分页就默认新接口也不分页；
3. 存储格式必须先分流：已确认的少量数据使用JSON单信封，其他数据使用Parquet+Snappy列式存储；未提供数据量结论时默认使用Parquet，不允许AI自行选择JSON；
4. 调度参数固定使用`biz_date=$[yyyy-mm-dd-1]`，代码只读取替换后的`YYYY-MM-DD`值，不再做日期加减；
5. 凭据只通过受控配置资源或凭据服务获取，禁止把APP ID、Secret、AK/SK、数据库账号密码写入代码；
6. EXT字段必须与实际OSS文件Schema一致，DWD必须显式列字段，禁止`SELECT *`；
7. 生成后必须补充空源保护、唯一键检查、数量关系校验和真实上下游依赖；
8. 本样例只覆盖到MaxCompute DWD。后续DWS存储在MySQL，ADS由前端或应用经受控后端接口写入，禁止据此在MaxCompute生成DWS或ADS；
9. 若实际接口采用Parquet、增量水位或历史分区表，只复用总体链路，不得照搬本样例的JSON信封和最新全量表写法。

### 9.2 参考一：少量数据的领星到OSS PyODPS节点

### 9.5 参考四：MaxCompute DWD表

### 9.6 参考五：OSS到MaxCompute DWD清洗节点

节点名称：`dwd_lx_basic_seller`  
上游依赖：`lx_basic_seller`  
节点参数：`biz_date=$[yyyy-mm-dd-1]`

```sql
SET odps.namespace.schema = true;
SET odps.sql.type.system.odps2 = true;
SET odps.sql.hive.compatible = true;

ALTER TABLE ext.lx_basic_seller_raw
ADD IF NOT EXISTS PARTITION (dt = '${biz_date}')
LOCATION 'oss://oss-cn-shenzhen-internal.aliyuncs.com/gq-lakehouse/guqiao_ods/lx_basic_seller/dt=${biz_date}/';

WITH seller_source AS
(
    SELECT
        sync_time,
        pos,
        item
    FROM ext.lx_basic_seller_raw
    LATERAL VIEW POSEXPLODE(data) exploded AS pos, item
    WHERE dt = '${biz_date}'
      AND dataset = 'lx_basic_seller'
      AND biz_date = '${biz_date}'
),
seller_clean AS
(
    SELECT
        (
            (
                UNIX_TIMESTAMP(CAST(sync_time AS DATETIME)) * 1000
                + CAST(FLOOR(CAST(pos AS DOUBLE) / 4096) AS BIGINT)
                - 1288834974657
            ) * 4194304
            + 1 * 131072
            + 1 * 4096
            + CAST(pos AS BIGINT)
            - CAST(FLOOR(CAST(pos AS DOUBLE) / 4096) AS BIGINT) * 4096
        ) AS id,
        CAST(
            CONCAT(
                REPLACE('${biz_date}', '-', ''),
                LPAD(CAST(pos + 1 AS STRING), 7, '0')
            ) AS BIGINT
        ) AS relate_id,
        item.sid AS sid,
        item.mid AS mid,
        NULLIF(TRIM(item.name), '') AS name,
        NULLIF(TRIM(item.seller_id), '') AS seller_id,
        NULLIF(TRIM(item.account_name), '') AS account_name,
        item.seller_account_id AS seller_account_id,
        NULLIF(TRIM(item.region), '') AS region,
        NULLIF(TRIM(item.country), '') AS country,
        CAST(item.has_ads_setting AS STRING) AS has_ads_setting,
        NULLIF(TRIM(item.marketplace_id), '') AS marketplace_id,
        CAST(item.status AS STRING) AS status,
        CAST(sync_time AS DATETIME) AS create_time
    FROM seller_source
)
INSERT OVERWRITE TABLE dwd.lx_basic_seller
SELECT
    id,
    relate_id,
    sid,
    mid,
    name,
    seller_id,
    account_name,
    seller_account_id,
    region,
    country,
    has_ads_setting,
    marketplace_id,
    status,
    create_time
FROM seller_clean;

SELECT
    COUNT(*) AS row_count,
    COUNT(DISTINCT sid) AS distinct_sid_count,
    SUM(CASE WHEN sid IS NULL THEN 1 ELSE 0 END) AS null_sid_count,
    COUNT(DISTINCT id) AS distinct_id_count,
    COUNT(DISTINCT relate_id) AS distinct_relate_id_count,
    MAX(create_time) AS latest_sync_time
FROM dwd.lx_basic_seller;
```

新代码生成要求：

- 注册EXT分区后先执行空源保护，再覆盖DWD；本示例现有SQL未单独阻断0行，新生成代码必须补充；
- JSON信封使用`POSEXPLODE(data)`展开，并通过`dt`、`dataset`和信封`biz_date`三重限定本批次；
- DWD写入字段必须与DDL顺序完全一致；
- 最新全量表使用整表`INSERT OVERWRITE`，历史表使用已确认的分区覆盖策略；
- Snowflake兼容ID示例可复用，但必须确认稳定排序、批次规模和唯一性；
- 质量检查至少包含记录数、业务唯一键、空主键、重复主键和同步时间；
- DWD质量校验通过后，才允许触发MySQL DWS任务。
